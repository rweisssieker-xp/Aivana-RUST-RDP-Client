# Task 4 design: failed repair and restoration guidance

Preparation only. Product changes, Cargo, and commits wait for the Wave 2 `BEGIN` signal and Tasks 1–3. Tests below use state transitions, fake adapters, or loopback endpoints; no customer host is contacted.

## Current behavior and concrete gaps

- `execution::Run::finish_health` sends a failed post-change functional check to `Restore` when the service changed, and directly to `Failed` when it did not. `advance` stops at `Failed`, `Restored`, or `Unknown`; `interrupt_after_restart` marks unfinished targets unknown. Existing tests cover successful restoration and some interruption, but do not exercise failed restoration, malformed mutation response, cancellation with a pending second target, or a full failing verification path through the UI driver.
- `execution_panel` saves before dispatching each remote change and health check. Save failure blocks dispatch. The cancellation path detaches the current job and calls `execution_fail`, which marks the current target unknown. A canceled remote job can still have effects; the UI needs precise next steps for this and for failed restoration. The current generic “Rollout stopped” label does not distinguish `Failed`, `Restored`, and `Unknown` and can suggest that restoration was a transaction rollback.
- `workflow::start_with_profiles` checks the reviewed digest. The runner journals a step before issuing its action, stops after an error, and never automatically compensates. `load_journal` marks running/awaiting-evidence runs interrupted. Existing loopback tests already show a failing HTTP step does not launch the next step and a changed review digest is rejected. Extend only uncovered boundaries, notably cancellation while waiting for evidence and persistence failure before a modifying action.
- The test lab already distinguishes `passed`, `returned`, and `checkpoint_removed`; a returned VM is not necessarily settled until the checkpoint is removed. Its panel gives a generic worker-failure notice. Keep clone trial guidance distinct from service restoration and avoid claiming that a service state or VM checkpoint reverses all external effects.

## Proposed minimal change

1. Introduce a small pure function near the service execution UI (or in `execution.rs` if useful for tests) that maps the current target phase, whether apply may have started, and the recorded functional/restoration evidence to short status and next-step text. Render it for the selected target. `Failed`: functional check failed without a change to restore; inspect check and target, then prepare a new reviewed run. `Restored`: original service state was verified, functional repair failed; check application and dependent systems separately before any new plan. `Unknown`: remote execution or restoration may still have effects; inspect target and durable journal, establish actual service/application state, then prepare a new reviewed run. `Restore` in progress: restoration is being attempted; result is pending. Do not offer same-run retry or next-target approval in these states. Say explicitly that restoration verifies only the measured service state, not transaction rollback.
2. Ensure UI guidance names the failed functional check and records its time/detail without promoting service-state verification to application success. If a restoration mutation returns mismatched/malformed evidence or the job fails, transition to `Unknown`, persist it, and leave subsequent targets untouched. Preserve the existing journaling-before-mutation and profile/proof gates.
3. Add succinct workflow status guidance beside the journal: failed step, canceled/interrupted in-flight step, and separately prepared recovery require inspection and fresh review. Keep recovery as a separately reviewed plan; do not imply automatic compensation. For test lab, show phase-specific guidance for failed or incomplete trial: inspect saved journal, VM/checkpoint and guest state; no production proof from unsettled trial.

## Meaningful tests to add or strengthen

- `execution.rs`: two-target run with failed functional check, restoration response `verified=false` (or mismatched response), then `Unknown`; assert `finished`, `current == 0`, next target stays `Capture`, `successful == false`, and rehearsal `proof_for == false`. Also test verified restoration has the same rollout stop but remains `Restored`, preserving the distinction. Existing success/restoration tests should be reused rather than duplicated.
- UI driver or extracted gate: inject a failing journal save before `Apply` and assert no queued mutation; exercise cancellation of an in-flight fake job and assert `Unknown`, no later target dispatch, and no automatic retry. Keep state-machine assertions independent of UI label text.
- `workflow.rs`: retain existing changed-digest and failing-loopback-step tests; add an offline cancellation while awaiting manual checkpoint/procedure evidence, asserting terminal uncertain journal and no later step launch. For persistence failure, add a narrow test seam for journal storage if necessary, proving a failed save prevents any action dispatch. Avoid global app-data environment mutation that races other tests.
- `change_trial_tests.rs`: existing fake `return-failure`, `delete-failure`, and interrupted proof tests cover core trial outcomes. Add only a test if guidance needs a pure derived state: returned but checkpoint not removed is unsettled and never eligible as production proof; a failed return remains uncertain.
