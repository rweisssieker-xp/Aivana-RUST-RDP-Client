# Relayne: six integrated USP workflows

User authorized all six proposed capabilities: transferable demonstration, verified end-to-end execution, real rehearsal on selected test infrastructure, telemetry-based dependency analysis, shared live sessions and evidence-ranked recommendations. Preserve existing dirty changes and user data. No live authentication retry or external deployment is implied by implementation.

## Ownership
- transferable_workflows: teaching/vision core and panels, new transferable.rs. Automatic exact-frame OCR anchors, named parameterized procedures, target replay.
- live_collaboration: team service/client/panel, new collaboration protocol/panel. Explicit sanitized frame sharing, memberships/leases, annotations, immutable two-person approval.
- verified_execution: new execution.rs/execution_panel.rs. Staging mappings, identical plan digest, pilot/rollout, actual health probes and supported restoration.
- root: telemetry observations and graph, prerequisite-aware experience recommendations, shared hooks, integration and verification.

## Delivery gates
- [x] Automatic demonstrated-click anchors, reusable parameters, reviewed cross-host replay; complete procedure approval scoped to one destination, optional explicit next-target queue.
- [x] Persisted diagnose/change/health-check/restore execution with evidence for supported service states.
- [x] Real selected staging execution and hash-bound production eligibility; no automatic VM creation.
- [x] Telemetry-derived dependencies and targeted hypothesis probes; historical association kept explicit.
- [x] Shared latest frames, annotations, expiring control ownership and two-identity approvals (click-only).
- [x] Similar-incident recommendations qualified by prerequisites and historical outcomes; verified execution lessons derived automatically.
- [x] Integrated native GUI and meaningful local tests/build/capture.

Live infrastructure-dependent acceptance remains explicit. Tests use local loopback, generated frames and guarded service fakes; cargo runs are centralized to avoid Windows binary locks. No feature is called complete based only on a toggle or a stub.
