# Telemetrie, Ursachenprüfung und wiederverwendbare Lösungen

„Ursachen & Lösungen“ erfasst ausdrücklich ausgewählte direkte Windows-Ziele über WinRM mit der aktuellen Windows-Identität. Das unveränderliche Ziel wird beim Start an die Antwort gebunden. Erfasst werden Betriebssystemversion, lokale IP-Adressen, Dienste mit Prozess-ID, TCP-Endpunkte und Metadaten der letzten Systemfehler (Zeit, Provider, Ereignis-ID und Stufe). Keine Prozessbefehlszeilen, Event-Nachrichtentexte, Passwörter oder Paketdaten. Berechtigungs-/Erfassungsfehler erzeugen keinen vermeintlichen Befund. Jede Erfassung ist begrenzt; abgeschnittene Daten sind gekennzeichnet.

Die automatische Zuordnung benötigt eine beobachtete Established-Verbindung am Quellrechner, genau einen bekannten Zielrechner mit dieser IP und einen passenden Listen-Port am Ziel. Dadurch werden angenommene Rückwärts-Abhängigkeiten zu Client-Ephemeralports vermieden. Dienstzuordnung folgt der Prozess-ID des Listeners. Gemeinsam gehostete Dienste bleiben mehrere Kandidaten; eine Verbindung beweist noch keine fachliche Abhängigkeit. IPv4-mapped IPv6 wird normalisiert, mehrdeutige IP-Zuordnungen werden ausgelassen. Beobachtungen müssen zeitlich zusammenpassen.

Eine bewusste Pfadprüfung startet vom betroffenen Rechner einen auf fünf Sekunden begrenzten TCP-Verbindungsversuch zum beobachteten Zielport. Ergebnis, Zielbindung und Zeitpunkt werden gespeichert. Nichterreichbarkeit zusammen mit einem heute gestoppten, historisch zugeordneten Dienst ist eine Hypothese mit explizit historischem Zuordnungsdatum. Keine unbelegte Behauptung einer bewiesenen Ursache. Chronologisch angezeigte Fehlerereignisse berücksichtigen mögliche Uhrabweichungen und fassen gleiche Ereignisse zusammen.

Die Lösungsbibliothek vergleicht Störungstext, Protokoll, optionalen OS-Versionspräfix und erforderliche installierte Dienste. Voraussetzungen benötigen frische, passende Telemetrie. Fehlende oder widersprüchliche Voraussetzungen sperren die direkte Übernahme. Der Planinhalt wird über SHA-256 exakt verglichen; erfolgreiche Ergebnisse benötigen passende Belege. Angezeigt werden dokumentierte Zielergebnisse einschließlich Fehlern/Unterbrechungen, keine erfundene Erfolgswahrscheinlichkeit. Die Übernahme erzeugt einen neuen ungeprüften Auftrag ohne Ausführung.

Zusätzlich werden abgeschlossene geprüfte Dienstabläufe automatisch aus dem Ausführungsjournal als Lösungen abgeleitet. Test- und Produktionsresultate bleiben getrennt; Dienst, Sollzustand und Funktionstest definieren die Lösung unabhängig vom Host. Vorher-/Nachher-Belege und Lauf-/Zielreferenzen bleiben nachvollziehbar. Eine erneute Verwendung bereitet nur einen Entwurf vor: Zielzuordnung, Vorprüfung, gültiger Testlauf und Freigabe sind erneut erforderlich.

Speicher: `relayne-telemetry.dpapi` (maximal 128 Beobachtungen, 1024 Verbindungen, 512 Proben) und `relayne-solutions.dpapi` (maximal 256 registrierte Lösungen), atomar und mit Windows DPAPI. Der Benutzer hat die Auswahl einer isolierten lokalen Testumgebung delegiert; Funktionsprüfungen verwenden bewachte PowerShell-Fakes und Loopbackserver. Das ersetzt keine produktive WinRM- oder RDP-Abnahme.

Implementierungsgrundlagen: [Get-NetTCPConnection](https://learn.microsoft.com/en-us/powershell/module/nettcpip/get-nettcpconnection?view=windowsserver2025-ps), [Win32_Service](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-service).
