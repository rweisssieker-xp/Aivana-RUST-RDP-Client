# Independent approval signing

`relayne_approval` is an offline console tool, separate from both the investigator and executor. It never performs network requests or provider actions. Use a signing workstation controlled by the independent reviewer; neither service host should hold its private key.

1. Create an Ed25519 private key in your approved protected key storage. For example, an existing operator-managed OpenSSL installation supports `openssl genpkey -algorithm Ed25519 -outform DER -out reviewer.pk8`. Restrict file permissions and use your organization's key lifecycle policy; this example does not configure secure storage for you.
2. Export its public key: `relayne_approval public-key reviewer.pk8 new-public.json`. Register only the resulting base64 public key against the reviewer's configured identity, tenant and sites. Both service processes use the same reviewed public-key policy.
3. Create a proposal in the investigation service. Save the complete `response.propose` or `response.challenge` JSON response to a file on the signing workstation through your approved transfer process.
4. Inspect it: `relayne_approval inspect challenge.json`. Verify the tenant, case, target, site, classification, action, parameters, policy and expiry against the requested measure. The tool refuses mismatched displayed grants, unknown domains/actions, noncanonical grants, malformed scope and expired challenges.
5. After that review: `relayne_approval sign reviewer.pk8 challenge.json reviewer new-approval.json --reviewed`. The flag records an explicit signing operation; it does not attest that a human review occurred. The signer must differ from the proposer. The server additionally checks the signer's configured role, public key and scope. Critical/Tier0 actions need two independently managed signing identities and keys.
6. The original proposer opens the separate executor console and supplies the proposal ID plus an array containing the approval JSON objects. Investigation credentials are not forwarded by the browser. The executor independently validates the signature and current scope/version/budget/expiry/stop/recovery gates before its at-most-once dispatch.

The tool only signs the exact supported Microsoft Graph session-revocation approval domain. All outputs require new files and never overwrite keys or prior approvals. It reads at most 4 KiB of key material and bounded challenge input. No private key or secret is printed. A correct signature proves the approved message and signing key, not the provider action's effectiveness; outcome verification remains separately recorded.
