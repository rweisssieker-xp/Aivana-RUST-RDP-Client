# Relayne isolated Hyper-V lab

The Testlabor page provisions a Generation 2 Windows VM from a user-selected **offline, standalone, read-only VHDX**. It creates a differencing child disk, a unique private switch, and a uniquely named VM with 2 GB startup RAM. No host/production network connection is created. The adapter does not enable Hyper-V or elevate the application. Run Relayne elevated on a supported, already configured Hyper-V host.

Before creation, detach the template from every registered VM and mounted VHD session, and set its ReadOnly file attribute. Keep the template unchanged while children exist. Supply a Windows 10/Server 2016 or later Generation 2 image whose setup is complete and whose local guest credentials are known. Licensing and image preparation are supplied by the operator. Secure Boot uses Hyper-V's normal Windows defaults.

1. Run the read-only host preflight. It reports the module, administrator token, VMMS state and PowerShell Direct parameter availability. Missing Hyper-V produces a real error.
2. Select a template and review the exact new VM name, source and destination. Execute the reviewed creation.
3. Select the resulting lab and enter guest credentials. Choose an exact service and desired Running/Stopped state. Review and execute the rehearsal. PowerShell Direct authenticates to the VM by its recorded ID without networking. The adapter changes that guest service and waits up to 30 seconds for the requested status. Failed checks attempt to restore the original Running/Stopped state and report whether restoration succeeded. Successful changes stay in the clone. The PowerShell Direct service itself is excluded.
4. Read the saved before/desired/after/pass/failure/restore evidence. The plan hash covers the VM ID, service and desired state. An optional HTTP GET probe runs inside the guest after the service change. Only literal 127.0.0.1/::1 HTTP URLs without user-info, query or fragment are accepted. The probe disables redirects, proxies and credentials, limits response headers to 16 KiB and decoded body to 65,536 characters, and uses 10-second network timeouts/body deadline checks. It checks the expected HTTP status and optional body text marker; failed health checks restore the original service state. The URL, expected status and marker are included in the plan hash. This evidence covers only the selected service and health endpoint and does not authorize a production change.
5. Review cleanup. It verifies exact VM ID, name, owner note, disk, network adapter and private switch ID/type; checks foreign adapters and child-parent association; then stops/removes the owned VM and switch and deletes only the child disk. The original template is never deleted or merged. Empty/configuration directories and the audit journal remain.

Journals live beneath the application data `test-labs/<UUID>/journal.dpapi` directory and use Windows CurrentUser DPAPI. The adapter checkpoints resource IDs immediately after creation and before/after tests and cleanup. Each action reloads the current encrypted journal. Journal reads are capped at 1 MiB; guest user/service/password inputs are bounded at 256/128/4096 bytes. Recorded errors redact the supplied credentials and are length-limited; guest failure evidence records the failed stage and exception type, never arbitrary response bodies. Guest passwords are passed through child-process stdin, not command-line arguments, and are not journaled. GUI password input clears when execution begins. Neither PowerShell nor Rust promises complete memory erasure.

Actions time out after 180 seconds. A timeout, process/host crash, or journal write failure can leave resources behind or leave an ID unrecorded. Reload the journal and inspect Hyper-V before retrying. Missing/mismatched ownership fails closed; the adapter does not guess ownership by name, scan for orphan resources to delete, or recursively remove directories. If the VM/switch was removed between mutation and checkpoint, manual reconciliation may be necessary. A failed guest connection is recorded as failure; wait for Windows boot and retry with valid credentials. There is no automatic boot-readiness polling or production deployment.

Development verification: generated PowerShell parses; guarded fake cmdlets verify preflight JSON, foreign-VM cleanup refusal, actual service apply/verify, verification-failure restoration and credential exclusion from results/journals. Loopback HTTP fixtures verify passing health and failed-marker restoration. Rust includes equivalent Windows tests, health URL validation and journal schema tests. The development host does not expose Get-VM, so real Hyper-V provision/guest/cleanup acceptance remains unverified. No real Hyper-V resources were created during development.

Official references: [New-VHD differencing disks](https://learn.microsoft.com/en-us/powershell/module/hyper-v/new-vhd), [private virtual switches](https://learn.microsoft.com/en-us/powershell/module/hyper-v/new-vmswitch), [PowerShell Direct requirements and execution](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/manage/manage-windows-virtual-machines-with-powershell-direct).
