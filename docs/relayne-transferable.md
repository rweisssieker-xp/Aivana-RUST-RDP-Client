# Demonstrate once, apply across hosts

The native teaching panel records a source session, proposes portable word targets from the exact displayed click frame, and replays reviewed steps on an explicitly selected destination session. The destination can have another session ID and resolution. Procedure files do not contain a source-session binding.

## Workflow

1. Select the source desktop and start a new demonstration. This explicit action starts one local Windows OCR worker. The input boundary supplies the displayed frame; pointer clicks retain the press frame until the matching release. Only successful engine inputs are observed.
2. Stop recording and wait for the bounded OCR queue to finish. Clicks directly inside a unique recognized word become proposed portable targets. Nearby context is recorded as displacement in target-word heights. Review every proposal. Unknown icons, wordless controls, ambiguity, sensitive text, missing exact frames, and queue overflow leave coordinate steps requiring manual anchoring.
3. Name the procedure, provide success/recovery notes, and optionally rename text placeholders to parameters such as `service_name`. Enter no credentials in notes. Save to the DPAPI library (32 named procedures maximum). Saving an existing name replaces it. Legacy `teaching.dpapi` procedures remain loadable.
4. Select a destination desktop and explicitly adopt it as the replay target. Read its current image with local OCR. A portable step resolves visible words and relative context on that destination; the preview displays the actual proposed destination coordinates. It never substitutes source coordinates. Legacy raw coordinate clicks require anchoring before transfer; raw scroll steps require manual execution and removal.
5. Supply a fresh parameter value when its step is reached. Values are held only in memory, never serialized, and cleared on sending, cancellation, target reset, or stale approval. Each step requires approval bound to the current destination session, frame hash and capture timestamp. Changes invalidate approval.
6. Optionally configure an expected visible status word and context after each step and/or for the final result. Run exactly one reviewed input step through the native engine. For configured assertions, Relayne automatically reads subsequent destination frames and advances only when the expected label resolves uniquely in OCR belonging to the exact current frame. This read-only wait does not require repeated approval. A newer frame alone never satisfies the assertion. Without a configured assertion, inspect a frame captured after sending, compare it with the stated criterion, and explicitly confirm. Switching targets or losing the connection resets progress, values, approval, and evidence.

## Whole-procedure approval and multiple destinations

The optional whole-procedure review lists every step, parameter name, postcondition and final condition. It is available only when every step is a portable semantic click or a named parameter, every step has an explicit OCR assertion, a final assertion exists, all parameter values have been supplied without control characters, and policy does not deny an action. Coordinates, opaque text placeholders, navigation keys, and scroll steps must be reviewed into supported steps first. No shell command or authentication action is generated by this workflow.

The deliberate **Ablauf für dieses Ziel freigeben** action authorizes the entire reviewed procedure for one explicitly adopted connected destination. Approval expires after five minutes and is bound by SHA-256 to the full procedure, in-memory parameter values, selected profile configuration, connection start timestamp, and destination session. Editing any bound content invalidates it. Parameters are never saved in the library and are cleared on completion or cancellation.

During an approved run, each next input resolves against OCR matching the current destination frame in the same UI turn as dispatch. An old frame approval is never reused. Each postcondition is checked on a frame captured after sending. A missing expected status can be an intermediate loading screen: the run waits without further input until the status appears within the eight-frame/30-second bound. Ambiguous matches stop immediately; missing fresh OCR prevents input and eventually stops the run. An edited profile must also still match the original connection's recorded source before any approval is issued or accepted. Cancellation, manual remote input, focus loss, connection changes, profile changes and expiry revoke approval. Completion records the exact final visible-state evidence, not a backend transaction claim.

The connected-target queue holds up to 16 chosen destinations. **Nächstes verbundenes Ziel aus Warteschlange übernehmen** explicitly selects the next destination and resets state and values. Each destination receives a fresh review, parameter values and its own whole-procedure approval. The queue never opens a connection or authenticates. This supports deliberate repeated host rollout without per-click approvals; it is not an unattended fleet broadcast.

## Resource bounds and evidence limitations

- One teaching OCR worker, two queued frames, one retained pointer-press frame; teaching frames above 32 MiB are not queued. The underlying Windows OCR operation has a 20-second deadline. A new demonstration waits for the previous worker to finish. No worker starts before recording is explicitly enabled.
- The procedure contains at most 200 steps; library files are bounded to 4 MiB. OCR screenshots are not persisted by this workflow. Recognized sensitive rows are removed before deriving anchor metadata. This heuristic is not a universal detector of secrets; review anchor labels before saving.
- Geometry supports movement and approximately uniform scaling through relative text height. Language changes, changed labels, nonuniform layouts, occluded controls, and multiple indistinguishable candidates block and require a new anchor. It does not infer icons or application control roles from OCR.
- Assertion polling shares the existing single vision worker and requests at most eight distinct frames during a 30-second check window. Missing, ambiguous, old, wrong-session or failed OCR remains unverified. Retrying the result check sends no remote input. Final proof is recorded as the exact verified image hash and timestamp; it is historical evidence, not a promise that the state remains unchanged.
- A visible-label assertion proves the configured text was visible, not causation or a backend business transaction. A label already visible before execution can still satisfy a presence assertion. Choose an informative status label and context. There is no hidden claim of universal application understanding. Per-step mode requests values per step; whole-procedure mode keeps reviewed values only during that target's run.

## Integration hooks

`src/main.rs`: register `mod transferable;`.

The existing focus-loss cancellation branch must also call `self.teaching.cancel_run("Fensterfokus verloren; Gesamtablauf angehalten")`. Ordinary frame changes invalidate only the old single-step approval: whole-procedure mode obtains fresh frame identity before each dispatch.

At each manual canvas input call, use `teaching_panel::send_teaching_manual_input(&mut self.engine, &mut self.teaching, frame, session_id, action)`. Supply the actual frame being displayed by that canvas, not a later frame from a drained event queue. The helper observes the input only when native send succeeds. The old `engine.take_manual_inputs()` loop must drain/discard without calling the recorder, preventing duplicate recordings. Existing `poll_teaching()` and `TeachingState::default()` remain the application integration points.

Tests cover moved/scaled targets on different sessions, ambiguous candidates, icon/no-word rejection, malformed parameter names, no serialized parameter values, stale hashes/timestamps/session IDs, reset behavior, stale asynchronous binding results, newer frames without expected labels, ambiguous result labels, and legacy procedures without assertion fields. Actual multi-host interaction still needs a user-authorized test environment.
