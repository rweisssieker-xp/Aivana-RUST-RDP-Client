# FR-18: signed A2 response executor

The only implemented external response is Microsoft Graph `POST /v1.0/users/{user-id}/revokeSignInSessions`. It is an A2 action with human signatures because session revocation is not reversible. A3 autonomous response remains disabled. Response is off by default.

## Deployment boundary

Run two `relayne_investigator` processes against the **same** SQLite database and the same validated policy file:

```text
relayne_investigator serve <config.json> <database>
relayne_investigator executor-serve <config.json> <database> 127.0.0.1:47842
```

`serve` binds `config.bind` and hosts the investigation UI, proposals, challenges and independent reconciliation. Its `response.execute` command is rejected in the router and again in the response handler; it never reads `graph_secret_env`. `executor-serve` requires a different numeric loopback bind, hosts its own small console at `/`, and accepts only authenticated `auth.me`, `response.status`, `response.execute` and `service.stop` commands through `/api/command` or MCP. It starts no investigation worker and cannot propose, reconcile, resume or call a collector. A request body or ordinary configuration field cannot change the process role. The main UI links to the executor console without passing credentials. Browser origin and Host checks bind each console to its own loopback address.

The crash and replay guarantee assumes the shared SQLite database has not been maliciously edited or rolled back. Both processes require database write access, so the database itself is not a tamper-resistant security boundary between those accounts; protect its directory and retain independent audit records.

Use a dedicated **OS service account** for each process as well as a separate **Entra application identity** for the executor. Give the main account its investigator/collector environment and no `graph_secret_env`; give the executor account its own response secret and no collector/source secrets. Set the response application's Graph permissions to the minimum required for `revokeSignInSessions`; a separate optional user read permission is needed to observe `signInSessionsValidFromDateTime`. Do not reuse the response client UUID with an enabled read source or collector, or its secret environment reference with any read source, enabled collector, operator bearer token, CMDB/ticket adapter, or notification webhook. Environment reference comparisons are case-insensitive. Make policy, executable and signer public keys administrator controlled. Both accounts require the least filesystem access needed to share the SQLite database, WAL and SHM files; the executor also needs read access to its config. Neither account should be allowed to read the other account's secret store. Protect the shared database from other local principals. SQLite WAL, transaction fences, one-time proposal/target constraints and shared stop/restore state preserve the dispatch ledger across both processes; a database restore still needs external reconciliation.

On Windows, register **two separate supervised tasks/services**, each under its own service account, with the command lines above. Have the executor's account retrieve its Graph secret from an account-restricted secret vault at startup and inject only `graph_secret_env` into that process environment. Have the main account retrieve only read-source secrets. A supervisor must launch the binary and restart it on failure; the binary is not itself a Windows Service Control Manager service. Keep vault access and the database directory ACLs separate. For an isolated test, two PowerShell shells launched under those two accounts can use the same commands; set the response variable only in the executor shell. Bind the executor to a separate loopback port and restrict access to both ports with local firewall/proxy policy. Do not set the response secret as a machine-wide environment variable.

The executor needs all configured **operator bearer tokens** at startup to authenticate the same named users and roles as the main process. This is distinct from the Entra application secret. The original proposer, who must be an incident lead or administrator, sends the signed execution request to the executor console using their own token. A reviewer signs the challenge outside either service. The executor does not hold private signing keys. If an operator calls `service.stop` on either service, both see the same persistent stop state; only the main service can resume after its recovery checks. Start the main service first so an absent stop record cannot be interpreted as a resume by the executor.

## Policy and dispatch

The `response` config rejects unknown fields. Enabling it requires an Entra tenant UUID and separate Graph client UUID/secret environment reference, named `policy_version`, UTC `valid_from` and `valid_until`, `max_approval_seconds` (1–600), `max_executions_per_day` (1–100), `max_runtime_seconds` (1–30), explicit targets and signers. Each target has an Entra user object UUID, configured site and classification (`normal`, `critical`, `tier0`). Signers are configured privileged users with base64 Ed25519 public keys and explicit site scopes. A normal target needs one independent signer; critical or Tier0 targets need two. The proposer cannot sign. Changing policy, signer keys, installed release component versions, or the fixed Graph action contract invalidates pending signatures. A2 has its own signed approval path and does not require an active A1 release; every executor deployment must update the component version when response behavior changes.

The proposer calls `response.propose` with `case_id`, `target_user_id` and `site`; the main service checks the open case and target scope, then reserves four provider calls and four 16 KiB response bodies from the persistent case/API/cost/runtime budgets: token, optional baseline read, mutation and optional follow-up read. `response.challenge` returns the exact canonical grant for signing. The grant binds tenant, case and version, proposal, user, site, classification, fixed action and empty parameters, proposer, issue/expiry times, nonce and policy hash. `response.execute` on the dedicated executor accepts the proposal ID and a list of `{actor, signature_base64}` approvals. It validates signatures, expiry, current case/policy/target, shared stop/restore gates and reservation, then commits one dispatch intent before any network mutation. The attempt ledger permits one dispatch per proposal and one per case/target; the daily cap is persistent.

A restart in `dispatching`, a timeout, malformed response or Graph error has an **unknown outcome**. The executor never retries the mutation. A different reviewer can call `response.reconcile` on the main service with `finding` (`effect_observed`, `no_effect_observed`, or `indeterminate`) and an `evidence_ref`. This is an attributable human evidence record, not machine proof and not permission to replay. A stop arriving after the final preflight check cannot recall an HTTP request already transmitted.

A successful Graph `value: true` reply is reported as `accepted_unverified`. The executor optionally reads the provider's `signInSessionsValidFromDateTime` before and after the mutation and records both values plus whether the watermark advanced. These reads can fail or lag, and another administrator can advance the watermark. Even a change does **not** prove that issued tokens or sessions became unusable. `effect_verified` and `technical_effect_verified` remain false. Independent effectiveness evidence needs separately authenticated observations and review. The fixed Microsoft login and Graph URLs, no redirects, maximum 16 KiB response body and bounded runtime apply to every provider request.

Back up the response ledger with the SQLite database. Restoring an older snapshot can lose a dispatch record for a real external effect. Restore pauses operation; before recovery acknowledgment and resume, compare the restored ledger with independently retained Entra audit records and reconcile any post-snapshot response attempts. Acknowledging restore cannot itself prove no external dispatch was lost.
