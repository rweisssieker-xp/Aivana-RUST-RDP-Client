# Per-monitor native session windows

In **Sitzungsfenster und Monitore**, a session with multiple configured RDP monitors offers **Ein Fenster pro Remote-Monitor**. Each native window paints the matching framebuffer UV region and uses the same region for pointer coordinates. Move each window to the desired local display and use **Vollbild umschalten** if appropriate. Save a named layout to persist the remote monitor index, topology and local window rectangle. Restore applies only to existing sessions and never opens or authenticates a connection.

Remote monitors to the left or above the primary monitor are normalized to framebuffer coordinates. The native panes wait without forwarding input until the received framebuffer dimensions match the configured topology. This avoids mapping input against an unconfirmed or stale desktop size. Monitor panes do not send independent dynamic-resolution requests. A focused pane owns input for its session; other panes do not release its held keys. Closing a pane releases held input and leaves the RDP session running.

The monitor definition comes from the connection profile. Configure and connect with that topology before opening monitor panes. Named layouts also retain a topology snapshot. Restoring a layout whose topology no longer matches the connected framebuffer leaves monitor panes waiting; use **Gesamter Desktop im Fenster** or establish the intended topology. The implementation does not claim automatic remote monitor discovery, automatic physical-display identification or reconnection on layout restore. Local display mapping uses saved desktop coordinates, so changed local display arrangements may require repositioning windows.

The existing `session-layouts.json` location remains compatible: old entries without monitor metadata continue to restore a full-desktop session window. New layouts save individual monitor entries. Loading is bounded to 1 MiB; invalid/non-finite window geometry and invalid monitor indices are skipped.

Tests `app::session_windows::tests` cover mixed monitor sizes, negative x/y origins, rejected stale framebuffer dimensions, invalid indices, coordinate overflow, serialization of remote monitor/local window mapping, legacy layouts, and distinct native viewport IDs. Pointer dispatch uses the application's shared `remote_canvas_region` / `viewport_to_remote` path, so image and input crop offsets agree. Actual multiple physical monitor placement remains a live UI verification step.
