# Relayne workflow packages (schema 1)

Current extensions: the inner schema-1 package is now distributed in an [Ed25519-signed envelope](relayne-signed-packages.md) (512 KiB outer bound); normal UI imports require an explicitly enrolled publisher key. The inner plan/package checks below still apply. [Demonstrated RDP procedures](relayne-icon-procedures.md) can run as typed workflow actions, with complete parameter preflight before any earlier action and per-request nonces for actual UI completion. Runtime values are separate from the exported plan.

Incident links use uniquely matching local SSH transport snapshots. A demonstrated RDP action additionally passes that snapshot to the UI and checks it against the actual session source before dispatch. Manual RDP attestations and HTTP/WinRM actions remain unbound rather than asserting a profile identity they have not established. The fixed WinRM adapter uses current Windows authentication on port 5985; a nonempty workflow `target.user` or another declared port is rejected instead of silently ignored.

The Workflows view executes a deliberately reviewed serial plan: preconditions, action steps, then application verification. Every SSH/WinRM target and command, HTTP endpoint and assertion, manual RDP checkpoint and declared restore step participates in the reviewed SHA-256 digest. Changing the plan invalidates approval. Import is inert and rejects unknown fields, unsupported schema, checksum mismatches and packages over 256 KiB. Plans allow at most 32 total steps. A checksum is not a signature and provenance is an unauthenticated author claim.

SSH and fixed WinRM operations use the existing bounded JobQueue (120-second subprocess deadline, bounded output). Assertions fail on command failure, missing expected output or output truncation. Preconditions allow only GET, fixed WinRM queries and manual checkpoints. SSH and mutating WinRM operations are rejected as preconditions. GET endpoint semantics must still be reviewed; an endpoint can implement side effects despite its HTTP verb. SSH authentication uses the configured native OpenSSH identity, WinRM uses native Windows authentication. There is no model-generated command execution path.

HTTP steps allow GET or form POST, expected status, optional body substring, and JSON Pointer/value equality assertions. Redirects are disabled; each request has a 20-second timeout and a 256 KiB response cap. For a login/session/test sequence, put literal form fields in `form`, password field-to-slot mappings in `secret_fields`, then enter slot values in the masked runtime JSON field. Cookies stay in worker memory, partitioned by exact scheme/host/port; supported cookies are host-only session cookies with explicit Path=/. Missing Path, Domain, Expires and positive Max-Age are rejected; zero/negative Max-Age removes the cookie. Cookies with another path are rejected. Origins and cookies per origin are capped at 32. System proxies are disabled. All secret slots must be present before any step starts. Secret submission requires HTTPS except literal loopback test addresses. Runtime slot values and response bodies are never included in exports or journals. Do not hard-code credentials into URLs, commands, assertions, or literal form fields; those are portable plan data. Secret memory is dropped at run completion, not guaranteed zeroized.

RDP steps pause at the declared target and expected result. The core accepts explicit operator evidence. The app also offers optional native OCR proof against the selected connected RDP session: the declared target must match its host, profile name or UUID, and a fresh frame captured after reaching the checkpoint must contain the exact expected word uniquely. Proof includes frame/session/time evidence; this verifies a visible word, not arbitrary application semantics. The per-checkpoint token prevents old proof from satisfying a later identical checkpoint. No automatic connection or clicking occurs. Manual evidence remains explicitly labeled as operator attestation.

The encrypted DPAPI journal is durably written before each step. Startup marks an unfinished run as interrupted with uncertain remote outcome. There is no automatic resume or replay. Cancellation stops subsequent steps and cancels command jobs; an in-flight HTTP mutation may finish before cancellation is observed. The UI records that uncertainty. A separate encrypted history retains up to the latest 50 runs within 8 MiB with per-step timestamp and actual endpoint evidence. Package target IDs cannot claim a trusted profile binding; workflow records remain unbound in incident hypotheses until independently matched to trusted profile snapshots. Execution targets are bound by the reviewed digest. Corrupt existing stores block execution rather than being silently replaced. Persistence failure prevents subsequent step launch.

Restoration is never automatic: 'Prepare declared restore for review' creates an editable plan using the explicitly declared restore actions. Review its preconditions and assertions for the restored state, then approve separately. A declared compensation is not a transactional rollback and cannot prove reversal of remote side effects.

Export creates a new file and refuses overwrite. A package contains schema, explicit numeric recipe_version (MAJOR.MINOR.PATCH), provenance, complete plan and SHA-256 integrity digest. Recipe version defaults to 1.0.0 and is editable at export. The checksum binds both schema and recipe version. Earlier development packages missing recipe_version must be recreated; import rejects them rather than silently changing their checksum. It contains neither runtime secrets nor execution authorization. Rebinding targets or editing tests changes the digest and needs fresh review.

Validation includes local loopback HTTP login/session cookies and JSON application assertions, HTTP status and JSON assertion failures, redirect rejection, package tamper/schema/unknown-field handling and review invalidation. A Windows end-to-end test runs the workflow engine, checks encrypted journals/history and interruption uncertainty, and proves failure prevents the next endpoint from being contacted. No remote credentials or remote mutations are used by those tests.




The UI shows a readable plan grouped into Voraussetzungen, Schritte, Prüfung and Wiederherstellung, including protocols, endpoints, commands and expected outcomes. Advanced JSON editing is collapsed. Three inert presets prepare HTTP login plus application verification, SSH plus HTTP verification, or RDP/OCR plus HTTP verification. Presets use reserved .invalid example targets or explicit placeholders; loading a preset makes no connection and clears approval. Configure real targets and expected results, then review and approve explicitly.
